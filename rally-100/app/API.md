# RALLY 100 app: backend contract

This is the single contract between the RALLY 100 database and every screen. The SQL implements it, the screens call it, and the tests check it. If code and this file disagree, fix one of them; never let them drift.

Product rules come from `rally-100/BLUEPRINT.md`. Architecture rules come from the repository `CLAUDE.md` (RALLY-owned IDs, money in integer cents, append-only ledger, server-authored truth, idempotent writes, team scoping).

## 1. Shape

- **Backend**: the existing RALLY Supabase project. Everything RALLY 100 adds lives in its own schema, `rally100`. Nothing in RALLY's `public` schema is created or altered. RALLY 100 reads `public.profiles`, `public.teams` and `auth.uid()` only.
- **RPC only**: clients never read or write `rally100` tables. Tables have RLS enabled, no policies and no grants to `anon` or `authenticated`. Every client operation is a function `rally100.<name>(...)`: `SECURITY DEFINER`, `set search_path = ''`, every identifier schema-qualified, `revoke all ... from public, anon, authenticated, service_role`, then `grant execute ... to authenticated` for API functions only. Internal helpers (prefixed `_`) are granted to nobody.
- **Exposure**: the schema must be added to Supabase **Project Settings → Data API → Exposed schemas** (`rally100`). Clients call `POST {url}/rest/v1/rpc/<name>` with headers `apikey`, `Authorization: Bearer <access token>`, `Content-Type: application/json`, `Content-Profile: rally100`, `Accept-Profile: rally100`. The body is a JSON object of named parameters. Every function returns one `jsonb` value.
- **Auth**: same accounts as the RALLY sales app. Email and password via Supabase auth (`/auth/v1/token?grant_type=password`, `refresh_token`, `/auth/v1/signup`, `/auth/v1/recover`, `/auth/v1/logout`). New sign-ups get RALLY's least-privilege profile (role `rep`, no team). Placement on a team stays a server-side act by leadership, exactly as in RALLY.

## 2. Roles and scope

Resolved server-side on every call by `rally100._caller()`, never accepted from the client.

| Caller | `public.profiles.role` | Scope |
|---|---|---|
| Rep | `rep` | Own List Entries only |
| Leader | `leader` or `manager` | Every rep with the same `team_id` (`public.my_team_id()`) |
| Owner | `owner` | Every team |

`_caller()` raises `rally100: not signed in` when `auth.uid()` is null, `rally100: no team` when the profile has no `team_id`, `rally100: disabled` when `profiles.disabled`. All three use `errcode '42501'`. A leader or owner may also build their own list; every rep function works for every role on the caller's own entries.

Errors: authorization failures use `errcode '42501'` and messages starting `rally100: `. Validation failures use `errcode '22023'` and a message `rally100: <code>` where `<code>` is a stable snake_case token the client maps to wording (for example `rally100: invalid_phone`). Clients show the mapped wording, never raw database text.

## 3. Vocabulary and fixed values

- **Platforms**: `Instagram`, `Snapchat`, `TikTok`, `Facebook`, `X`, `LinkedIn`, `Discord`, `Other` (Other requires `other_app`).
- **Tags**: `School`, `Sports`, `Work`, `Gym`, `Neighborhood`, `Family`, `Group chat`, `Hobbies/Clubs/Community`, `Lost touch`, `Other`.
- **Scenes** (`scene` key, clears-at): `phone` 5, `chats` 5, `shift` 3, `lunch` 3, `bus` 3, `gym` 3, `street` 3, `lost` 3, `family` 3, `clubs` 3, `roommates` 3, `bignight` 3, `plusone` 3, `mutual` 3. Entries added outside a Scene have `scene = null`.
- **Stages** (ordered): `added`, `intro_planned`, `introduced`, `meeting_scheduled`, `meeting_completed`, `commitment_confirmed`, `agreement_signed`, `start_confirmed`, `arrived`.
- **Outcomes**: `follow_up`, `not_interested`, `do_not_contact` (or null).
- **Interest**: `unknown` (default), `interested`, `maybe`, `not_interested`.
- **Requirements**: 1 Meeting completed, 2 Commitment confirmed, 3 Agreement signed, 4 Start date and travel plans confirmed.
- **Reward kinds**: `list` ($100, one per rep, ever), `referral` ($100, one per Person, ever), `incentive` (owner-defined amount).
- **Reward statuses**: `in_progress`, `ready` (Ready for review), `approved` (every screen shows "Pending pay"), `paid` (every screen shows "Pay issued"), `needs_correction`. A reversal is a flag on the record, never a sixth status.
- **Milestones**: 10, 25, 50, 75, 100 counted contacts; XP 50, 100, 200, 300, 500.
- **Levels** (XP): Rookie 0, Scout 150, Connector 400, Operator 800, Prowler 1300, Apex 2000.
- **Money**: integer cents everywhere (`amount_cents`), currency USD.

## 4. Core rules the server enforces

1. **Normalization.** Phone: digits only, a leading `1` dropped from 11 digits; stored only as exactly 10 digits or `''`. A non-empty phone that does not normalize to 10 digits raises `invalid_phone`. Handle: trimmed, lowercased, leading `@` and any `https://host/` prefix removed, trailing `/` `?` `#` parts removed. A handle without a platform raises `platform_required`; `Other` without `other_app` raises `other_app_required`. First name is required (`first_required`), at most 60 characters; last name at most 60; notes at most 2000; tags must be in the list.
2. **Complete** = first, last, a 10-digit phone, a handle and a platform (plus `other_app` for Other).
3. **Counted** = complete AND not removed AND not held as a duplicate AND its Person is not marked `do_not_contact`. A rep's count is the number of counted entries. Not interested and Follow up later still count.
4. **Within-rep duplicates.** On every save, an entry with a phone or a handle is compared with the same rep's other entries that are not removed and not held: same phone, or same platform plus handle (plus `other_app` for Other). Pairs the rep marked "Different people" are skipped. If a match exists, the NEWER entry (later `created_at`) gets `held_of = <older id>` and stops counting; the older keeps counting. Name-only matches never hold.
5. **Resolving a duplicate.** "Same person": the older entry takes any field it is missing from the newer one, tags are united, notes appended; the newer is removed with `merged_into`; no XP is granted for the merge (the older's completion XP key is recorded if it becomes complete). "Different people" is allowed only for a same-phone match and needs a reason: both entries record each other in `kept_with`, the newer is released and counts, and its XP key becomes per-entry.
6. **Persons (master CRM).** When an entry first has a phone or handle and is not held, it is linked to a Person: an existing Person whose identifiers share the phone, or the platform plus handle, AND whose last name matches case-insensitively (or where both phone and handle match). Otherwise a new Person is created from the entry, and if a strong signal matched a Person with a different last name, a `possible_matches` row is recorded for leaders. Every identifier an entry carries is added to its Person. Persons are never deleted.
7. **XP is game progress only, never money.** Keys are unique per rep in `xp_events`, so nothing is ever earned twice. `cc:<phone>` (or `cc:<phone>#<entry id>` after "Different people") +10 when an entry becomes counted; `ch:<same>` +3 when that entry was added under a chain prompt; `sc:<scene>` +15 when a Scene's counted entries reach its clears-at; `ms:<N>` at each milestone; `in:<person id>` +100 when a leader confirms the rep's introduction was received. Removing and re-adding grants nothing new.
8. **List Completion Reward.** The first time a rep's count reaches 100, the server inserts the single `list` reward (unique per rep) at `ready`. While `ready` and the count is under 100, reads report `hold = true`. Approval needs count ≥ 100 AND a recorded spot-check for that reward.
9. **Referral Reward.** The first time any rep records an introduction of a Person (`record_intro`), the server inserts the single `referral` reward for that Person (unique per Person) at `in_progress` with no credited rep. When the fourth requirement is confirmed, the server credits **whoever signs the person first**: the rep with the earliest `recorded_at` among that Person's introductions with `received_at` set, and moves the reward to `ready`. With no received introduction, the reward stays `in_progress` and is flagged `no_intro` for the owner. Unticking a requirement before approval returns the reward to `in_progress` and clears the credit. After `approved` or `paid`, unticking is refused (`locked_reward`).
10. **Requirements** are confirmed one by one by a leader or the owner, with a name and date. A stage change never confirms one. Requirement 4 needs `start_date` and either a `travel_note` or `travel_na = true`.
11. **Do not contact** removes the Person from every rep's count. Only a leader or the owner sets it; only the owner clears it.
12. **Review.** Leaders approve or return rewards of reps on their team; the owner may approve any. Nobody approves a reward credited to themselves (`self_involved`); the owner's own rewards are approved only by another owner. Only the owner marks pay issued, reverses, or closes a leaving rep's unpaid rewards.
13. **Leaving reps.** `close_rep_unpaid(rep, reason)` reverses every unpaid reward of that rep with an internal reason (`left` or `no_show`) and no rep-facing reason. Paid rewards are untouched. Nothing about this rule is ever returned to a rep.
14. **Audit.** Every write appends to `rally100.audit` (actor, team, entity, entity id, action, detail). Reward transitions also append to `rally100.reward_events`. Neither table is ever updated or deleted.
15. **Idempotency.** `save_entry` creates with a client-generated UUID, so a retried create is an update. Every transition function checks the current status and refuses or no-ops a repeat; a second `mark_pay_issued` raises `already_paid`.

## 5. Tables (`rally100` schema)

No client grants on any table. RLS enabled on all.

- `entries`: `id uuid pk` (client-generated), `team_id uuid not null`, `rep_id uuid not null`, `person_id uuid null`, `first_name text`, `last_name text`, `phone text check (phone ~ '^(\d{10})?$')`, `handle text`, `platform text`, `other_app text`, `tags text[]`, `notes text`, `scene text null`, `chain_hit bool`, `held_of uuid null`, `kept_with uuid[]`, `kept_reason text`, `merged_into uuid null`, `removed_at timestamptz null`, `completed_at timestamptz null`, `verified_at timestamptz null`, `verified_by uuid null`, `created_at timestamptz`, `updated_at timestamptz`. A stored generated column `is_complete boolean`.
- `persons`: `id uuid pk`, `first_name`, `last_name`, `stage text`, `outcome text null`, `outcome_date date null`, `outcome_note text`, `interest text`, `responsible_leader uuid null`, `next_action text`, `next_action_owner uuid null`, `next_action_date date null`, `meeting_at timestamptz null`, `meeting_how text`, `meeting_note text`, `start_date date null`, `travel_note text`, `travel_na bool`, `merged_into uuid null`, `created_at`, `updated_at`.
- `person_identifiers`: `person_id`, `kind` (`phone` or `handle`), `value` (phone digits, or `<platform>:<handle>` with `Other:<app>:<handle>`), unique `(kind, value, person_id)`.
- `possible_matches`: `id`, `person_a`, `person_b`, `signal`, `status` (`open`, `linked`, `dismissed`), `created_at`, `resolved_by`, `resolved_at`.
- `introductions`: `id uuid pk`, `person_id`, `rep_id`, `entry_id`, `status` (`planned`, `introduced`), `channel` (`text`, `call`, `in_person`, `other`), `said` (`in`, `maybe`, `not_for_them`, `didnt_say`), `note`, `intro_date date`, `recorded_at timestamptz null` (server time when it became introduced), `received_by uuid null`, `received_at timestamptz null`; unique `(person_id, rep_id)`.
- `requirements`: `(person_id, req smallint 1..4)` pk, `confirmed bool`, `confirmed_by uuid`, `event_date date`, `note text`, `updated_at`.
- `messages`: `id`, `person_id`, `rep_id`, `body`, `created_at`, `read_by`, `read_at`.
- `notes`: `id`, `person_id`, `author`, `body`, `created_at` (leader notes, append-only).
- `xp_events`: `(rep_id, key)` pk, `points int`, `kind text`, `created_at`.
- `badges`: `(rep_id, badge)` pk, `created_at`. Server-derived: `reader` (3 Scenes cleared), `full` (100), `first_intro`, `matchmaker` (3 received introductions). Client-reported through `award_badge`: `sprinter`, `clean_sweep`.
- `acks`: `(rep_id, version)` pk, `accepted_at`. Current disclosure version: 1.
- `rewards`: `id uuid pk`, `kind`, `team_id`, `rep_id uuid null` (credited rep; null for a referral until credited), `person_id null`, `incentive_id null`, `amount_cents int`, `currency text default 'USD'`, `status`, `flags text[]` (`no_intro`; read models add `rep_closed` while the credited rep is closed), `spot_check_id null`, `approved_by`, `approved_at`, `paid_on date`, `paid_method text`, `paid_reference text`, `paid_by`, `reversed_at`, `reversed_by`, `reversed_reason text` (internal), `rep_reason text` (rep-facing, may be empty), `correction_note text`, `correction_by`, `created_at`, `updated_at`. Partial unique indexes: one `list` per `rep_id`; one `referral` per `person_id`.
- `reward_events`: append-only ledger: `id bigserial`, `reward_id`, `action`, `from_status`, `to_status`, `actor`, `note`, `created_at`.
- `spot_checks`: `id`, `reward_id`, `rep_id`, `leader_id`, `results jsonb` (`[{entry_id, result: looks_real|unclear|not_real}]`), `note`, `created_at`.
- `incentives`: `id`, `name`, `pictures jsonb` (array of `data:image/jpeg;base64,...` strings, at most 4, each at most 400,000 characters), `prize_cents int`, `how_to_earn text`, `status` (`draft`, `published`, `off`), `created_by`, `created_at`, `updated_at`.
- `audit`: `id bigserial`, `actor`, `team_id`, `entity`, `entity_id`, `action`, `detail jsonb`, `created_at`.
- `rep_closures`: `id`, `rep_id`, `reason` (`left`, `no_show`), `closed_at`, `closed_by`, `reopened_at null`, `reopened_by null`. At most one open closure per rep (partial unique index). A rep is "closed" while one is open (rule 13).
- `spot_samples` (append-only): `id`, `reward_id`, `rep_id`, `entry_ids uuid[]`, `drawn_by`, `drawn_at`. The walkthrough sample for a list reward, drawn by the server; the current one is the newest drawn after that reward's last spot-check.

## 6. Functions

Forty functions. Every function returns `jsonb`. Times are ISO strings; dates `YYYY-MM-DD`; money `amount_cents`. Names shown to clients are `profiles.name`, falling back to the part of `email` before `@`.

### 6.1 Everyone

- **`whoami()`** → `{user:{id,name,email,role,team_id,team_name}, ack_version_required:1, ack_accepted:bool}`. For a caller with no team returns `{user:{...}, no_team:true}` instead of raising, so the app can explain placement.
- **`accept_ack(p_version int)`** → `{ok:true}`.

### 6.2 Rep functions (caller's own entries; any role)

- **`rep_state()`** → everything the rep app shows:
  `{count, drafts, held, xp, level:{name,min,next_name,next_min}, milestones:[10,25,...reached], badges:[...], scenes:{<key>:{names,lit,drafts,cleared}}, entries:[entry...], list_reward:{status,hold,amount_cents,approved_at,paid_on,reversed,rep_reason,correction_note} | null, referrals:[referral...], intros:[intro...], incentives:[{id,name,pictures,prize_cents,how_to_earn}] (published only), awards:[{id,incentive_id,name,amount_cents,status,paid_on,reversed,rep_reason}], leader:{name} | null}`.
  - `entry` = `{id, first_name, last_name, phone, handle, platform, other_app, tags, notes, scene, chain_hit, is_complete, counted, held_of, held_of_name, kept_with, removed, merged_into, created_at, completed_at, missing:[...labels], person_id, dnc:bool}`. Removed entries are included with `removed:true` (merged ones excluded).
  - `intro` = one per live, unheld entry for which THIS rep planned or recorded an introduction (another rep's activity never creates or changes a card): `{entry_id, person_id, name, status (planned|introduced), recorded_at, received:bool, channel, said, intro_date, credited:'me'|'other'|null, stage, outcome, outcome_date, interest, requirements:[{req,confirmed,by_name,event_date}, ... req 4 adds travel_na] | null, next:{who:'you'|'leader', name, text} | null, meeting_at, leader_name}`. `leader_name` and a leader `next.name` are always the rep's own team leader. Only planned: stage `intro_planned`, interest `unknown`, no requirements or meeting, `next` = you, "make the introduction". `credited:'other'` (the referral went to another rep): only the rep's own facts; `stage` is their own (`intro_planned`/`introduced`) and `outcome`, `interest`, `requirements`, `next`, `meeting_at` are null. Otherwise `next` is the leader's explicit next action when its owner is this rep or a leader of this rep's team; else null while an outcome is set; else "schedules the meeting" (before a meeting is scheduled) / "holds the meeting" until anything is confirmed, then the first unconfirmed requirement ("confirms the meeting", "confirms the commitment", "confirms the agreement", "confirms start date and travel plans"), and null once all four are confirmed.
  - `referral` = for each Person this rep recorded an introduction of, or whose referral is credited to this rep: `{person_id, entry_id, name, status, credited:'me'|'other'|null, amount_cents, confirmed_count, requirements:[...], approved_at, paid_on, reversed, rep_reason, correction_note}` (`correction_note` only while the reward is `needs_correction`). `entry_id` is the rep's own entry for that Person: match by it, not by name. When credited to another rep, only `{credited:'other', name, entry_id}`.
- **`save_entry(p jsonb)`** creates or updates by `p.id` (UUID). Fields: `id, first_name, last_name, phone, handle, platform, other_app, tags, notes, scene, chain_hit`. Absent keys leave a field unchanged on update. Refuses an id owned by another rep (`not_found`) and a removed or merged entry (`entry_removed`). Returns `{entry, effects:[effect...], count, drafts, held, xp, level}`, where `effect` is one of `{type:'xp', points, key}`, `{type:'milestone', n}`, `{type:'scene_cleared', scene}`, `{type:'level', name}`, `{type:'held', older_id, older_name, by:'phone'|'handle'|'person'}`, `{type:'list_ready'}`. A rep holds at most 500 live entries and 2,000 entry rows in all (`list_full`).
- **`resolve_duplicate(p_entry uuid, p_decision text, p_reason text)`**, decision `same` or `different` → same shape as `save_entry` with `entry` = the surviving or released entry. `different` is allowed on a same-phone match or on a hold that came only through a shared Person (the two entries share neither phone nor handle; the released entry gets a Person of its own); on a handle match it raises `handle_match_needs_fix`; a missing reason raises `reason_required`.
- **`remove_entry(p_entry uuid)`** / **`restore_entry(p_entry uuid)`** → same shape as `save_entry`. Restore re-runs the duplicate check; no XP is granted twice; it is refused at 500 live entries (`list_full`).
- **`plan_intro(p_entry uuid)`** → `{intro}`. Requires a complete, counted entry (`entry_not_complete`, `held_duplicate`, `do_not_contact`). Creates or keeps the rep's introduction at `planned`; Person stage moves to `intro_planned` if it was `added`.
- **`record_intro(p_entry uuid, p_channel text, p_said text, p_note text, p_date date)`** → `{intro}`. Same preconditions. Sets the introduction to `introduced` with `recorded_at = now()` (only the first time); stores `said` and sets Person interest from it (`in`→interested, `maybe`→maybe, `not_for_them`→not_interested, `didnt_say`→unknown) only if no leader has set interest; Person stage moves to `introduced` if lower; responsible leader defaults to the team's first leader (by `created_at`) if none; inserts the Person's referral reward at `in_progress` if none exists.
- **`set_follow_up(p_entry uuid, p_date date, p_note text)`** → `{intro}`. Rep may set Follow up later only on their own introduction (planned or recorded, else `intro_required`), from a complete, counted entry (`entry_not_complete`, `held_duplicate`, `do_not_contact`), while the Person stage is `added`, `intro_planned` or `introduced` (`stage_locked`), not over a leader's Not interested (`outcome_locked`), and not when another rep has recorded an introduction and this rep has not (`stage_locked`).
- **`tell_leader(p_entry uuid, p_body text)`** → `{ok:true}`. Body 1 to 1000 characters.
- **`award_badge(p_badge text)`** → `{badges}`. Only `sprinter` and `clean_sweep`; idempotent.

### 6.3 Leader functions (leader, manager or owner; team scope, owner all teams)

Leaders of the team that RUNS a Person change it; others with the Person in scope only read it (`not_allowed`): the team of the rep who holds the referral credit; before credit, of reps whose introduction was received; before that, of reps who recorded one; while nobody has introduced the Person, any leader in scope. This governs `set_requirement`, `set_stage`, `schedule_meeting`, `set_interest`, `set_next_action` and every `set_outcome` except setting `do_not_contact`, which any leader in scope may do. The owner is never restricted. `person.controls` and `q.controls` say whether the caller runs the Person.

- **`team_state()`** → `{reps:[{id,name,email,role,disabled,closed,count,drafts,held,last_activity,list_reward:{id,status,hold,spot_checked,reversed,amount_cents,paid_on}|null, intros_received, signed}], queues:{new_intros:[q], meetings:[q], follow_ups:[q], confirmations:[q], reviews:[r], messages:[m], matches:[pm]}, counts:{...}}`.
  - `q` = `{person_id, name, stage, outcome, outcome_date, meeting_at, reps:[names in scope], next_action ('' unless the caller runs the Person), controls, confirmed_count, updated_at}`. `new_intros`: introductions recorded and not yet received. `meetings`: stage `meeting_scheduled`. `follow_ups`: outcome `follow_up` with `outcome_date` ≤ today. `confirmations`: stage ≥ `meeting_completed` with fewer than 4 confirmed and no blocking outcome.
  - `r` = `{reward_id, kind, status, rep_id, rep_name, person_id, person_name, amount_cents, hold, spot_checked, flags}` for rewards at `ready` or `needs_correction`; `flags` may hold `no_intro` and `rep_closed`.
  - `m` = unread rep messages `{id, person_id, person_name, rep_name, body, created_at}`.
  - `pm` = open possible matches `{id, a:{id,name}, b:{id,name}, signal}`.
- **`person_detail(p_person uuid)`** → `{person, entries:[{rep_id,rep_name,added_at,tags,introduced:bool,recorded_at,received_at}] (reps outside the caller's scope appear as {rep_name:'A rep on another team'}), identifiers:[...], requirements:[{req,confirmed,by_name,event_date,note}], reward:{...}|null, notes:[...], messages:[...], history:[{at, actor_name, action, detail}, newest first, at most 100]}`. Refuses a Person outside scope (`not_found`). `person` = `{id, first_name, last_name, name, stage, outcome, outcome_date, outcome_note, interest, dnc, responsible_leader, responsible_leader_name, next_action, next_action_owner, next_action_owner_name, next_action_date, meeting_at, meeting_how, meeting_note, start_date, travel_note, travel_na, confirmed_count, controls, merged_into, created_at, updated_at}`; the next action is shown only to the team that runs the Person and its owner only when in the caller's scope (every `{person}` answer below is built the same way). `reward` is null unless the reward is the caller's (rule 12 scope). For leaders, history leaves out rep actions (creating, planning or recording an introduction, messages, follow-ups) by anyone outside their scope, whatever that person's role, and shows each action's allowlisted detail keys only: rep ids only in scope, never the owner's internal reasons, payment method or reference.
- **`confirm_intro_received(p_person uuid, p_rep uuid)`** → `{ok}`. Sets `received_by/received_at` once; grants the rep `in:<person>` +100 XP; sets the responsible leader to the caller if none; checks the rep's `first_intro` and `matchmaker` badges.
- **`set_stage(p_person uuid, p_stage text, p_date date, p_note text)`** → `{person}`. Leader-owned stages are `meeting_scheduled` onward; a backward move needs a note (`reason_required`).
- **`schedule_meeting(p_person uuid, p_at timestamptz, p_how text, p_note text)`** → `{person}`. Sets stage `meeting_scheduled` if lower.
- **`set_requirement(p_person uuid, p_req int, p_confirmed bool, p_event_date date, p_note text, p_start_date date, p_travel_note text, p_travel_na bool)`** → `{person, requirements, reward}`. Applies rules 9 and 10. Unticking needs a note (`reason_required`) and is refused once the reward is approved or paid (`locked_reward`). A caller who recorded an introduction of this Person may neither confirm nor untick (`self_involved`).
- **`set_outcome(p_person uuid, p_outcome text, p_date date, p_note text)`** → `{person}`. `follow_up` needs a date; `not_interested` needs a note; `do_not_contact` allowed; null clears an outcome, except clearing `do_not_contact`, which is owner-only (`owner_only`).
- **`set_interest(p_person uuid, p_interest text)`**, **`set_next_action(p_person uuid, p_text text, p_owner uuid, p_date date)`**, **`add_note(p_person uuid, p_body text)`**, **`mark_messages_read(p_person uuid)`** → `{ok}`.
- **`rep_list(p_rep uuid)`** → `{rep:{id,name}, count, entries:[entry...], sample:[entry...]}` for the walkthrough. `sample` is up to 5 counted entries drawn by the server with real randomness the first time the rep's list reward is open (`ready` or `needs_correction`) and kept: every call shows the same sample until a spot-check is recorded (redrawn if fewer than 3 still count). No open list reward: `sample` is `[]`. VOLATILE (the first call draws).
- **`record_spot_check(p_reward uuid, p_results jsonb, p_note text)`** → `{reward}`. Only for a `list` reward. Results name 3 to 5 entries of the current sample, each still counted (`spot_check_entry`; no sample drawn yet: `no_sample`); `looks_real` marks the entry verified. Rule 12 applies (`self_involved`, `owner_only`). Recording it uses the sample up.
- **`review_reward(p_reward uuid, p_action text, p_note text)`**, action `approve` or `needs_correction` → `{reward}`. `approve` needs status `ready` and, re-checked under the record's lock, the rule 8 or 9 conditions (`count_below_100`, `spot_check_required`, `no_credited_rep`, and all four requirements confirmed now, else `not_ready`); nothing is approved for a closed rep (`rep_closed`); `needs_correction` needs a note. Rule 12 applies (`self_involved`).
- **`resolve_correction(p_reward uuid, p_note text)`** → `{reward}`: `needs_correction` back to `ready`, by whoever raised it or the owner; never on a reversed record (`reward_reversed`).
- **`link_persons(p_match uuid, p_action text)`**, action `link` (merge B into A: identifiers, entries, introductions, requirements moved; refused when both have a referral reward, `both_have_rewards`) or `dismiss` → `{ok}`.
- **`award_incentive(p_incentive uuid, p_rep uuid, p_note text, p_request uuid)`** → `{reward}`. `p_request` is required (`request_required`): a UUID the client generates ONCE per award and resends on every retry; it becomes the reward's id, so a retry returns the award already made and creates nothing, while a new request for the same incentive and rep is a new award (weekly prizes). A `p_request` already used for anything else is `request_reused`. Incentive must be `published`; note required; creates an `incentive` reward at `approved` (rule 12 applies); never for a closed rep (`rep_closed`).

### 6.4 Owner functions

- **`owner_state()`** → `{totals:{reps, persons, counted, introductions, signed}, reps:[same as team_state.reps (including closed) plus team_id, team_name], funnel:{<stage>:n}, outcomes:{...}, rewards:{<status>:{count, amount_cents}}, payments:[last 50 paid], leaders:[{id,name,team_name,open_items}], pending_signups:[{id,name,email,created_at}], incentives:[all, any status]}`.
- **`owner_contacts()`** → `{rows:[{person_id, name, phone, handles:[...], reps:[names], team_names, stage, outcome, interest, created_at, requirements_confirmed, reward_status}]}` for search, filters and CSV export.
- **`owner_rewards(p_status text)`** → `{rows:[reward rows with rep and person names, all statuses when null]}`.
- **`mark_pay_issued(p_reward uuid, p_paid_on date, p_method text, p_reference text)`** → `{reward}`. Needs `approved`; method note required (`method_required`); `already_paid` on repeat; refused for a closed rep (`rep_closed`). Payment method and reference are the owner's alone: no leader read model carries them.
- **`reverse_reward(p_reward uuid, p_reason text, p_rep_reason text)`** → `{reward}`. Internal reason required.
- **`close_rep_unpaid(p_rep uuid, p_reason text)`**, reason `left` or `no_show` → `{closed:n}`. Records the closure (`rep_closures`) and reverses every unpaid reward; while it stays open nothing new is approved or awarded to the rep, and anything credited to them carries the `rep_closed` flag for leaders and the owner (never in `rep_state`).
- **`reopen_rep(p_rep uuid)`** → `{ok:true}`. Ends the closure for the future; past reversals stay as they are. A no-op for a rep who is not closed.
- **`correct_credit(p_reward uuid, p_rep uuid, p_reason text)`** → `{reward}`.
- **`clear_dnc(p_person uuid)`** → `{person}`.
- **`incentive_save(p jsonb)`** → `{incentive}`: create (no id) or update (`id`), fields `name` (required, at most 80), `pictures` (rule above, at least 1 to publish), `prize_cents` (≥ 0, required), `how_to_earn` (optional, at most 200), `status`.
- **`incentive_status(p_incentive uuid, p_status text)`** → `{incentive}`.

## 7. Client conventions

- Wording follows the blueprint. Approved shows "Pending pay"; paid shows "Pay issued" with the date. Money is never shown as earned, partial or pending before approval. Requirement codes never appear on rep screens.
- Rep writes go through an outbox: `save_entry` calls carry client-generated UUIDs and are replayed in order when the phone is back online. Until the server answers, a new tile shows the syncing state. Server counts always win.
- The owner's "Mark pay issued" is the only control that moves a reward to Pay issued. Nothing about the leaving-rep rule appears anywhere a rep can see.

## 8. Implementation notes

Decisions taken where this contract was silent or ambiguous, each the reading most consistent with its rules. Implemented in `rally-100/db/migrations/1001_rally100_v1.sql`; tested by `rally-100/db/test/run-tests.sh`.

**Errors.** Every message is exactly `rally100: <token>`. The three identity refusals keep their spelling (`not signed in`, `no team`, `disabled`; checked in that order, so a disabled account without a team hears `disabled`, from `whoami` too).
- `42501` (authorization): `not signed in`, `no team`, `disabled`, `not_allowed` (a rep calling a leader function; a leader resolving a correction someone else raised; a leader changing a Person their team does not run), `owner_only` (owner functions; clearing or replacing Do not contact; a leader approving, returning, spot-checking or awarding to an owner), `self_involved` (acting on your own reward; confirming your own introduction; confirming or unticking requirements of a Person you introduced), `not_found`, `append_only`.
- `not_found` is `42501`, following RALLY's turf functions: an id outside the caller's scope and an id that does not exist get the identical answer, so a guessed UUID learns nothing.
- `22023` (validation): `invalid_payload`, `invalid_id`, `first_required`, `name_too_long` (first or last over 60, incentive name over 80), `too_long` (any other free text over its limit: notes 2000, handle 100, other_app 40, messages and notes 1000 or 2000, reasons 300 or 1000, method and reference 200, next action 200, meeting how 40), `invalid_phone`, `platform_required`, `invalid_platform`, `other_app_required`, `invalid_tag`, `invalid_scene`, `entry_removed`, `invalid_decision`, `not_held`, `handle_match_needs_fix`, `reason_required`, `note_required`, `date_required`, `entry_not_complete`, `held_duplicate`, `do_not_contact`, `invalid_channel`, `invalid_said`, `stage_locked`, `outcome_locked`, `invalid_badge`, `invalid_version`, `invalid_stage`, `invalid_req`, `start_date_required`, `travel_required`, `locked_reward`, `invalid_outcome`, `invalid_interest`, `intro_not_recorded`, `not_list_reward`, `spot_check_size`, `spot_check_entry`, `invalid_result`, `invalid_action`, `not_ready`, `count_below_100`, `spot_check_required`, `no_credited_rep`, `reward_reversed`, `match_closed`, `both_have_rewards`, `not_published`, `name_required`, `prize_required`, `invalid_prize`, `too_many_pictures`, `picture_too_large`, `invalid_picture`, `picture_required`, `invalid_status`, `not_approved` (mark_pay_issued before approval), `method_required`, `already_paid`, `invalid_reason`, `not_referral`, `not_candidate`, `rep_closed` (approving, awarding or paying for a closed rep), `list_full` (500 live entries, or 2,000 entry rows), `request_required`, `request_reused` (award_incentive's idempotency key), `no_sample` (a spot-check before the walkthrough sample is drawn), `intro_required` (a follow-up with no introduction of your own).

**Calling.** Trailing optional parameters have `DEFAULT NULL` (notes, dates, reasons, R4 fields, `p_reference`, `p_rep_reason`, `owner_rewards.p_status`), so a client may omit them; PostgREST matches a function by its parameter names, so a misspelled key is a 404. Read functions (`whoami`, `rep_state`, `team_state`, `person_detail`, `owner_*`) are `STABLE`; `rep_list` is VOLATILE because its first call draws the spot-check sample.

**Entries and XP.**
- `completed_at` is the first moment the entry COUNTED; it is never cleared. Completion XP (`cc:`, and `ch:` with it, never alone) is granted only then, so remove and restore, Do not contact and its clearing, and blanking then retyping a different phone earn nothing again. Keys stay as rule 7 spells them, so re-adding a removed contact as a new entry also earns nothing.
- `scene` and `chain_hit` describe how a name was first added: taken on create, ignored on update (otherwise counted names could be walked from Scene to Scene for `sc:` XP).
- Duplicates are recomputed over the rep's whole live list on every list write (oldest first; an entry is held of the earliest unheld earlier entry it matches), so the result never depends on save order: removing the older releases the newer, restoring it holds the newer again. A third signal is added to phone and handle: two of one rep's entries linked to the same Person (only possible via another rep's identifiers or `link_persons`), because one Person counts once per rep; its `held` effect has `by:'person'`. The walk reads each shared key's members once, so a save stays near-linear (about 20 to 40 ms at the 500-entry cap).
- "Different people" needs different handles and either the same phone, or a hold that came only through a shared Person (the two share neither phone nor handle: another rep's identifiers joined them). In that case the entry leaves that Person for one of its own, taking with it any identifier no other entry on the old Person carries. In every case the released entry gets its own Person (Persons of its kept-with entries are never link candidates).
- List size: 500 live entries per rep and 2,000 entry rows in all (`list_full`), checked under the rep lock.
- "Same person": the merge records the survivor's `cc:` key at 0 points. Count-driven effects (milestones, `scene_cleared`, the reader and full badges, the list reward) are evaluated after EVERY write that can move a count, including merges, restores, Do not contact changes and Person merges, because they are keyed to the count, not to the action.
- `missing` uses the client's labels: `First name`, `Last name`, `Phone`, `Social handle`.

**Persons.** A last-name match needs a non-empty last name; both-signal matches win, then the oldest Person. A `possible_matches` row is written only when a new Person is created. A Person created from a nameless draft takes its name from the first entry that has one. Leaders see a possible match only when both Persons are in their scope; the owner sees all. `link_persons` merges B into A unless only B has a referral reward (the Person with a reward record survives); notes, messages and history stay on the record they were written to and are read through the merge family.

**Scope.** Membership is read live from `profiles.team_id`; `entries.team_id` and `rewards.team_id` are snapshots for history. A leader's Person scope is any Person with an entry by a rep on their team; changing a shared Person belongs to the team that runs it (section 6.3). A leader's reward scope is the credited rep's team; an uncredited referral is visible to the leaders of every rep who planned or recorded an introduction, or, while nobody has, to any leader with the Person in scope. A leader's `person_detail` history is filtered per row (rep actions by anyone outside their scope are dropped, whatever that actor's role) and per key (an allowlist per action; rep ids only in scope; never the internal reversal or credit-correction reasons, the payment method or reference); its `entries` list live (not removed, not merged) entries.

**Introductions and referrals.**
- `_intro_entry` order: `entry_not_complete`, then `held_duplicate`, then `do_not_contact`.
- Intro cards come only from the rep's own planned or recorded introduction (section 6.2); `next` follows progress, not stage, so a Person at 4 of 4 has no next step and an outcome clears it.
- "Interest set by a leader" means an audit row `set_interest` exists for the Person; `set_outcome('not_interested')` also sets interest and writes that row (blueprint: "The outcome Not interested also sets it").
- A requirement confirmation creates the Person's referral record if none exists (blueprint), so a fully confirmed Person with no introduction reaches the owner flagged `no_intro`. `confirm_intro_received` re-applies rule 9 to an In progress record that already has all four confirmations (crediting it and clearing `no_intro`). A credit the owner set with `correct_credit` is kept at the fourth confirmation; any untick clears it.
- Nobody confirms receipt of their own introduction (`self_involved`).
- `set_stage`: a leader moves forward only to `meeting_scheduled` or later (`invalid_stage` otherwise), back to any stage with a reason; the same stage is a no-op; `p_date` and the note are kept in the audit row.
- `set_follow_up` (rep) belongs to the rep's own introduction (blueprint: "on their own introductions before handoff"), so the follow-up lives on their own card; see section 6.2 for its refusals.
- A leader who recorded an introduction of a Person (building their own list) is the would-be credited rep: another leader or the owner confirms its requirements (`self_involved`).

**Rewards.**
- List and referral rewards are 10000 cents USD; an incentive award is its prize at award time. Totals in `owner_state.rewards` exclude reversed records; clients show money only for approved and paid.
- Retried approve and needs_correction are no-ops; a reversed record cannot be approved, spot-checked, resolved or paid (`reward_reversed`), and an untick leaves it where it was. A spot-check is allowed at `ready` or `needs_correction` under rule 12, from the server's current sample only; the newest one is the reward's `spot_check_id`.
- LOCKS. `set_requirement`, `review_reward`, `mark_pay_issued`, `reverse_reward`, `correct_credit` and `close_rep_unpaid` lock the reward row (`FOR UPDATE`) before they read it, and approving, awarding, paying and closing also take a per-rep closure lock first, in that order; so an untick and an approval, or a payment and a closure, can never both pass their checks against the same moment (`db/test/race-test.sh` proves both orders with two sessions).
- Closures are recorded state (`rep_closures`). The `rep_closed` flag is computed at read time from the open closure, so it disappears when the owner reopens the rep; it is never stored and never shown to the rep.
- Re-confirming an already confirmed requirement on an approved or paid reward is a no-op; unticking one is `locked_reward`. `correct_credit` is refused once approved or paid (`locked_reward`; reverse first) and needs a rep with an entry on the Person (`not_candidate`).
- `mark_pay_issued` with no date records the org's today. `close_rep_unpaid` reverses with the internal reason and `rep_reason = ''`; the rep's read models show such a record as `reversed: true` with an empty reason and never the internal one. `paid_method` and `paid_reference` appear only in the owner's read models.
- `team_state.reps` lists every profile on the team (all roles, disabled ones too) and adds `disabled` and `closed`; its `list_reward` adds `reversed`, `amount_cents` and `paid_on`. For the owner, `team_state` covers every team. `signed` counts the rep's credited, unreversed referral rewards; `last_activity` is their latest audit row. Any outcome takes a Person out of `new_intros`, `meetings` and `confirmations`.
- Incentive pictures must be `data:image/jpeg;base64,` strings (raster only); `prize_cents` must be a JSON integer.

**One org day.** "Today" (follow-ups due, default dates) is the date in `America/Chicago`, set in one place, `rally100._today()`. The blueprint recommends an owner "Org timezone" setting; change that one function if the office is elsewhere.

**History.** `audit`, `reward_events`, `xp_events`, `notes`, `spot_checks` and `spot_samples` refuse UPDATE, DELETE and TRUNCATE by trigger, even from the table owner. A rep's own follow-up is audited as `follow_up` (a rep action), a leader's as `outcome`.

**Not implemented (not in this contract).** Verify flags, reward reinstatement, Person split, leader-to-rep assignment lists, CSV export auditing, proposed-correction handling of phone and handle edits after an introduction.
